# Project structure

Directories are created **when the milestone that needs them arrives** — an empty folder teaches
nothing and hides which parts are actually in use.

```
car-service-management/
├── main.go                    composition root: read config, build, run
├── internal/
│   ├── config/                typed Config, loaded from the environment
│   ├── server/                Server struct, routes, middleware, handlers
│   ├── store/                 pgx pool + the SQL queries
│   └── db/                    sqlc-generated code — never hand-edited
├── views/                     .templ components + their generated *_templ.go
├── assets/                    reads Vite's manifest so templates can link the bundle
├── web/                       the Vite project
│   ├── package.json           frontend dependencies
│   ├── bun.lock               committed, so builds are reproducible
│   ├── vite.config.js         entry point, output directory, Tailwind plugin
│   └── src/
│       ├── app.js             the single JS entry point
│       └── app.css            Tailwind input
├── public/build/              Vite output — generated, git-ignored
├── sql/
│   ├── migrations/            golang-migrate .sql files, embedded and run at startup
│   └── queries/               the SQL sqlc reads
├── sqlc.yaml                  sqlc config: schema, queries, output
├── docs/
├── Makefile                   day-to-day commands — run `make help`
├── .env.example               config template; copy to .env
└── go.mod
```

## Why each directory exists

### `main.go` at the root
The composition root. It reads configuration, loads the asset manifest, runs migrations, opens the
database pool, builds the server, and starts it — so one file answers "how is this application
assembled?" It also declares the `go:embed` of `sql/migrations`, because embed paths are relative to
the package that declares them and only the root package can see that directory.

It stays small. All the interesting code lives in `internal/`.

### `internal/`
Go treats this name specially: **no code outside this module can import anything under
`internal/`.** The compiler enforces it, which means these packages can be renamed and refactored
freely.

### `internal/config/`
One `Config` struct describing everything the application needs at startup: environment, port,
database URL. Read once, validated once, passed onward.

The alternative — calling `os.Getenv` wherever a value is needed — is how you get a program that
half-starts and then fails on request #400 because a variable was missing.

### `internal/server/`
The `Server` struct owns the router and holds what handlers need: config now, the asset URLs, and
the database pool from Milestone 2. Handlers are methods on it, so they reach their dependencies
through the receiver rather than through package-level variables — which is what keeps them
testable.

Routes are registered in one file, so there is a single place to answer "what URLs does this
application respond to?"

### `internal/store/`
Owns the pgx connection pool and wraps the generated queries. `store.New` pings the database as it
opens the pool: a pool is lazy, so without that check a wrong password would not surface until the
first request.

The wrapper is deliberately thin — it adds context to errors and keeps the rest of the application
out of the generated package. `store.Customer` is a type *alias* for `db.Customer`, so there is no
hand-written struct to keep in step with the schema.

### `internal/db/`
sqlc's output, regenerated by `make sqlc` from `sql/queries/` and the schema in `sql/migrations/`.
Editing it by hand means losing the edit on the next generation. It is committed, so a build needs
only the Go toolchain.

### `views/`
Templ components, in one flat package. `templ generate` writes a `*_templ.go` beside each `.templ`
file, and those generated files are **committed** so `go build ./...` works with only the Go
toolchain installed.

A flat package keeps composition simple: any component can render any other without an import.

### `assets/`
Vite writes bundles with a content hash in the filename — `app-ZApCAbCH.js` — so browsers can cache
them indefinitely and still pick up changes immediately after a deploy. The cost is that no Go code
can know the filename in advance, so Vite also writes a manifest. This package reads it once at
startup and hands the URLs to the templates.

### `web/`
A self-contained Vite project: its own `package.json`, lockfile, config, and `node_modules`. Keeping
it in one directory means the frontend toolchain never clutters the repository root, and `bun` runs
inside it.

### `public/build/`
Vite's output, and the only directory the server exposes to the browser. Generated, so it is
git-ignored — `make assets` recreates it.

### `sql/`
Migrations and queries are both `.sql` but serve different purposes and change at different rates.
Migrations alter the schema and are **append-only forever**: once one has run anywhere, you write a
new one rather than editing it. Queries are edited freely. Separate directories stop you editing a
migration by accident.

Each migration is a pair — `000001_create_customers.up.sql` and `.down.sql` — so every change can be
rolled back. `main.go` embeds the directory with `go:embed` and `store.Migrate` applies whatever has
not run yet, before the server accepts requests. A deployed binary therefore carries its own schema:
one artefact to ship, and no way to run new code against an old database.

golang-migrate tracks progress in a `schema_migrations` table it manages itself.

## Naming conventions

- **Packages**: short, lowercase, one word — `config`, `server`, `store`. No underscores, no `utils`
  or `helpers` (a package named for what it contains resists becoming a junk drawer). Singular,
  unless the package genuinely is a collection: `views` holds views and nothing else, and matching
  the directory name is the stronger Go convention.
- **Files**: lowercase with underscores where needed — `home.go`, `server.go`. Tests sit beside
  their subject as `server_test.go`.
- **Database**: `snake_case`, plural table names (`customers`, `service_jobs`), `id` primary keys,
  `<table_singular>_id` foreign keys (`customer_id`), `created_at` / `updated_at` timestamps. Index
  every foreign key explicitly — PostgreSQL does it for primary keys, not for foreign keys.
- **Go identifiers**: `MixedCaps`, never `snake_case`. Exported only when something outside the
  package needs it — start unexported and promote when required.
- **Avoid stutter**: `store.Customer`, not `store.StoreCustomer`.
